**Finding: localStorage Token Storage XSS Surface (SEC-03):**
- File: `client/src/store/useAuthStore.js` (the `persist` middleware config)
- Both `token` (access JWT) and `refreshToken` are stored in `localStorage` via Zustand's persist middleware.
- Code snippet: The persist config showing `partialize` with token fields, and the `onRehydrateStorage` callback that uses `atob()`.
- Impact: Any XSS vulnerability in the application gives an attacker access to both tokens. The access token has 1h TTL, but the refresh token has 30-day TTL (and is not single-use per plan 02-01 findings). Combined, an XSS attack yields persistent 30-day access.
- Severity: HIGH
- Remediation: Move refresh token to httpOnly cookie (requires backend changes to set cookie on login/refresh and read from cookie on token refresh endpoint). Access token in memory-only (not localStorage) with refresh-on-401 pattern. Note: the CLAUDE.md project convention explicitly says "useAuthStore token stored in localStorage -- acceptable for JWT" — document this project decision but still flag the XSS surface as a finding.
- Also document the `atob()` usage at line ~87: client-side JWT decode without signature verification. The `isAuthenticated` flag is set based on `exp * 1000 > Date.now()` — a crafted token with future exp would appear valid on rehydration. Contained by server-side 401 on actual API calls, but the trust model is incorrect.
- Addresses: C-05, C-08

**Finding: Timing Attack Surface in Login (SEC-16):**
- File: `server/src/Controller/Auth/LoginController.php` line ~40
- Code snippet: `if (!$user || !$passwordHasher->isPasswordValid($user, $data['password']))` with `return $this->json(['message' => 'Invalid credentials'], Response::HTTP_UNAUTHORIZED);`
- Analysis: `isPasswordValid()` uses bcrypt via Symfony's `UserPasswordHasherInterface` — bcrypt comparison is inherently constant-time. However, the `!$user` short-circuit means that when a user does not exist, `isPasswordValid()` is never called. This creates a timing difference: non-existent user returns in microseconds, wrong password returns after bcrypt hash (~100ms).
- Resolve Open Question 2: Check if Symfony's PasswordHasher performs a dummy hash for null users. If it does, the timing is normalized. If not (likely — the `!$user` check is BEFORE the call), flag as MEDIUM.
- Severity: MEDIUM (response message is already generic "Invalid credentials" — timing alone reveals email existence but requires statistical analysis over many requests; rate limiting on /api/login_check mitigates further)
- Remediation: Perform a dummy `password_hash('dummy', PASSWORD_BCRYPT)` call when user is null to normalize timing. Or use Symfony's built-in authenticator which handles this.
- Addresses: (no specific concern ID — SEC-16 only)

**Finding: Account Enumeration via Registration (SEC-22):**
- File: `server/src/Controller/Auth/RegisterController.php` lines 58-63
- Code snippet: The two `findOneBy` checks returning "Email address already used" and "Username already taken"
- Contrast with LoginController line 40: generic "Invalid credentials"
- Impact: An attacker can enumerate registered email addresses and usernames by attempting registration. Combined with the timing oracle above, email existence can be confirmed through two independent channels.
- Severity: MEDIUM (common in many applications; no direct account compromise, but aids targeted attacks)
- Remediation: Return a single generic message "Registration failed — please check your input" for all conflict cases. Or move to email-based confirmation flow where registration always succeeds (sends confirmation email or shows generic success).
- Addresses: (no specific concern ID — SEC-22 only)

**Append a summary table** at the end listing ALL findings from both tasks in this plan.
