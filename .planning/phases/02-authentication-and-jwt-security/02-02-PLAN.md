**Step 1 — Resolve Open Question 1 (algorithm enforcement):**
Read `server/vendor/firebase/php-jwt/src/JWK.php` and `server/vendor/firebase/php-jwt/src/Key.php` to determine whether `JWK::parseKeySet()` embeds the algorithm from the JWKS `alg` field into each `Key` object. Specifically check:
- Does `JWK::parseKeySet()` call `new Key($keyMaterial, $alg)` where `$alg` comes from the JWKS JSON?
- Does `JWT::decode()` enforce the algorithm from the `Key` object when the third `$allowed` parameter is omitted?
- Check `server/composer.lock` for the exact firebase/php-jwt version installed.

Document the answer: if `Key` objects enforce RS256 from JWKS, the algorithm confusion severity drops from HIGH to MEDIUM (defense-in-depth gap). If not, it remains HIGH (exploitable).

**Step 2 — Write Algorithm Confusion Finding (SEC-F-010):**
- File: `server/src/Controller/Auth/GoogleAuthController.php` line 136-137
- Code snippet: `$keys = JWK::parseKeySet($jwks);` and `$payload = JWT::decode($idToken, $keys);`
- Severity: HIGH or MEDIUM (based on Step 1 result)
- Impact: Without explicit `['RS256']` as third argument, algorithm selection depends on library internals. Even if mitigated by Key objects, this is a defense-in-depth failure — a library update that changes Key behavior would silently re-expose the vulnerability.
- Remediation: `$payload = JWT::decode($idToken, $keys, ['RS256']);` — if v7 API does not accept a third argument, document the correct v7 API for algorithm restriction.

**Step 3 — Write Claim Validation Map:**
Read `GoogleAuthController.php` lines 139-158 and document each claim check:
- `iss` — is it checked? Against what values? (`accounts.google.com` and `https://accounts.google.com`)
- `aud` — is it checked? Against what value? (the Google client ID from env)
- `exp` — is it checked? (firebase/php-jwt handles this internally via `JWT::decode`)
- `sub` — is it checked? (used as `$googleId`)
- `email` — is it checked? (used for account lookup)
- `email_verified` — is it checked? (ABSENT — this is the CRITICAL finding in Task 2)

For each claim, document: claim name, verification status (CHECKED / ABSENT / DELEGATED-TO-LIBRARY), code line, and verdict.

**Step 3b — Document Missing Division Assignment (C-07):**
Read `GoogleAuthController.php` lines 86-97 (new user creation). Check whether `setDivision()` is called and whether it uses `User::DEFAULT_DIVISION` correctly. If the division assignment is missing or incorrect, write a MEDIUM finding (SEC-F-011) documenting the gap. If it is present and correct, note it as verified. Addresses: C-07.

**Step 4 — Write Error Handling Fragility Finding (merged: C-02 + C-18 + C-09):**
- Title: "GoogleAuthController Error Handling Fragility"
- File: `server/src/Controller/Auth/GoogleAuthController.php` lines 160-162 (bare catch), plus JWKS fetch logic
- Code snippet: The `catch (\Throwable) { return null; }` block
- Severity: HIGH
- Impact: The bare catch silences ALL verification errors including algorithm confusion attempts, expired tokens, signature failures, and JWKS fetch failures. There is zero logging. An attacker probing with crafted tokens gets the same response as a legitimate user with an expired token. Combined with the JWKS retry logic (C-18), a transient Google outage could trigger repeated JWKS fetches with no circuit breaker.
- Remediation: Replace with specific catches for `\Firebase\JWT\ExpiredException`, `\Firebase\JWT\SignatureInvalidException`, `\Firebase\JWT\BeforeValidException`. Log each failure type. Re-throw or log unexpected exceptions at ERROR level.
- Addresses: C-02, C-18, C-09

**This finding gets the full attack scenario narrative per locked decision (exception to standard 2-3 sentence format).**

**Finding: Email-Match Account Linking Without email_verified Check (SEC-F-012):**

Severity: CRITICAL

File: `server/src/Controller/Auth/GoogleAuthController.php` lines 68-99

Code snippet: The email-match branch that calls `$user->setGoogleId($googleId)` and `$entityManager->flush()` without checking `$payload->email_verified`.

**Full Attack Scenario Trace:**

Step 1 — Attacker registers at `POST /api/register` with `email: victim@example.com`, `username: attacker123`, `password: attacker_password`. The registration succeeds because the application has no email verification (C-29). The attacker now has a valid account with the victim's email address.

Step 2 — The real victim, who owns `victim@example.com`, later decides to log in using Google OAuth at `POST /api/auth/google`. Their Google account has `email: victim@example.com` and `email_verified: true`.

Step 3 — `GoogleAuthController::googleAuth()` calls `verifyIdToken()`, which returns the payload. The controller extracts `$email = $payload->email` and queries `$userRepo->findOneBy(['email' => $email])`.

Step 4 — The query finds the attacker's account (registered in Step 1 with the same email). The code enters the `if ($user)` branch at line 72.

Step 5 — The code executes `$user->setGoogleId($googleId)` and `$entityManager->flush()` — silently linking the victim's Google ID to the attacker's account.

Step 6 — `AuthTokenService::createTokenPair()` issues a JWT and refresh token for the attacker's user record. The victim receives a valid session for an account the attacker controls.

Step 7 — The attacker can still log in with `email: victim@example.com` and `password: attacker_password` via `POST /api/login`. They now have full access to an account that the victim believes is theirs.

**Impact:** Complete account takeover. The attacker controls the account before the victim ever logs in. The victim's Google login reinforces the attacker's control by linking the Google ID. No technical sophistication required — only knowledge that the victim uses the application.

**Remediation:**
```php
// Add before the email-match branch (line 71):
if (!isset($payload->email_verified) || $payload->email_verified !== true) {
    return $this->json(['message' => 'Email not verified by Google'], Response::HTTP_FORBIDDEN);
}
```
Additionally, the account-linking branch should require the user to be currently authenticated (logged in) before allowing Google ID linking, or send a confirmation email to the existing account.

Addresses: C-36 (GoogleAuthController edge cases), C-29 (no email verification)
