**Part A: Error Leakage Audit (SEC-09)**

1. Read `server/.env` for `APP_ENV` and `APP_DEBUG` values:
   - If `APP_DEBUG=1` or `APP_ENV=dev`: document the default development setting
   - Check `server/.env.prod.example` for production template values
   - Check `server/config/packages/framework.yaml` for `when@prod` overrides

2. Analyze what Symfony exposes in non-dev mode:
   - In `APP_ENV=prod` + `APP_DEBUG=false`: Symfony returns generic 500 error pages, no stack traces
   - In `APP_ENV=dev` + `APP_DEBUG=true`: Symfony profiler shows full stack traces, env vars, DB queries
   - Document the risk: if deployed without changing APP_ENV, full debug info is exposed

3. Check API error response format:
   - Read controller error responses in GoogleAuthController and ProfileController
   - Look for any `$exception->getMessage()` or `$exception->getTrace()` being returned to client
   - Look for any JsonResponse that includes internal paths or class names

4. Score:
   - If error messages in controllers leak internal details: raise finding
   - If APP_DEBUG/APP_ENV defaults are dev-mode and no production guard: document as finding with dual-context severity (same pattern as profiler)

**Part B: Bare Exception Patterns (SEC-18)**

5. Read `GoogleAuthController.php` around line 160 — the `catch (\Throwable)` block:
   - Document what exceptions are silenced (Google JWT verification failures, network errors, malformed tokens)
   - Check if there is ANY logging in the catch block
   - Score: if no logging and generic response, the catch block silences security-critical failures
   - Note: SEC-F-004 from Phase 2 already documented GoogleAuthController error handling fragility; Phase 4 finding should cross-reference but score the bare catch pattern specifically

6. Read `ProfileController.php` around line 81 — the `catch (\RuntimeException)` block:
   - Document what exceptions are caught (avatar upload failures from StorageService)
   - Check if there is logging
   - Score based on whether upload failure details are lost

7. Read `client/src/lib/axios.jsx` — check the response interceptor error handling:
   - Document if errors are caught and re-thrown, swallowed, or logged
   - This is a cross-reference for SEC-18 (frontend side)

8. Raise findings for each bare catch pattern:
   - GoogleAuthController: reference SEC-F-004 from Phase 2, add SEC-18 bare catch perspective
   - ProfileController: new finding if catch swallows diagnostics
   - axios interceptor: document pattern (may cross-tag with MAINT stream)

**Part C: Avatar CDN Cache Poisoning (SEC-20)**

9. Review Phase 3 SEC-F-017 (deferred to Phase 4):
   - Read the Phase 3 finding from 03-02-SUMMARY.md for context
   - Audit the R2 filename strategy: is the avatar filename a stable UUID or does it change on re-upload?
   - Check `server/src/Service/StorageService.php` for the key generation pattern
   - Check if R2 serves with Cache-Control headers
   - Check if content-type is enforced at CDN level or derived from the file

10. Resolve SEC-F-017 with final severity:
    - If filename is UUID-stable (same key on re-upload): cache poisoning is possible (old content cached)
    - If filename changes on each upload: cache poisoning mitigated
    - If R2 serves user-controlled content-type: additional concern
    - Score and document final severity (likely stays LOW based on Phase 3 preliminary assessment)

Write all findings to `findings/04-03-errors-deps-exceptions.md` with standard format.
