  <action>
1. Read `server/config/packages/nelmio_cors.yaml` — document the full config structure:
   - `origin_regex: true` with `allow_origin: ['%env(CORS_ALLOW_ORIGIN)%']`
   - Allowed methods: GET, OPTIONS, POST, PUT, PATCH, DELETE
   - Allowed headers: Content-Type, Authorization
   - max_age: 3600
   - Both `defaults` and `paths.'^/api'` sections duplicate the same allow_origin

2. Read all `.env*` files in `server/` to find `CORS_ALLOW_ORIGIN` values:
   - `server/.env` — check for default value
   - `server/.env.example` — check for template value
   - `server/.env.prod.example` — check for production template value

3. Scan git history for any committed production CORS value:
   ```bash
   git log --all -p -- '*.env*' '*.env.local' '*.env.prod' | grep -i 'CORS_ALLOW_ORIGIN'
   ```
   Also check for any committed `.env.local` or `.env.prod` files:
   ```bash
   git log --all --name-only | grep -E '\.env\.(local|prod)$'
   ```

4. Document findings:
   - If CORS_ALLOW_ORIGIN is `*` or `'^.+$'` (regex wildcard): raise as CRITICAL
   - If CORS_ALLOW_ORIGIN is a specific origin: raise as CLEAN or MEDIUM depending on specificity
   - If production value not discoverable from static analysis: raise as finding requiring production environment verification with conditional severity (MEDIUM if restricted, CRITICAL if wildcard)
   - Document `origin_regex: true` implications: if the value is a regex pattern, partial matches could widen the allowed origin set (e.g., `'^https://example\.com'` also matches `https://example.com.evil.com` without `$` anchor)

5. Write the CORS section of findings file with format:
   - Finding ID: SEC-F-019 (or appropriate next ID)
   - Severity: conditional (see above)
   - Evidence: nelmio_cors.yaml snippet + .env values found
   - Impact narrative
   - Remediation: set explicit production origin, ensure regex anchor with `$`
  </action>
