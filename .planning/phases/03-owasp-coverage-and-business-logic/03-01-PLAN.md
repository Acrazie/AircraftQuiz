**Finding 1 — type=null daily limit bypass (SEC-F-012, expected MEDIUM):**
- Trace ScoreController.php lines 52-65: `$type` is set to null when `$data['type']` is absent or not in `VALID_TYPES`
- The guard `if ($type !== null && ...)` at line 60 means the entire daily limit check is skipped for null-type submissions
- LP is still calculated and applied via `rankingService->calculateLpChange()` regardless of type value
- Read `RankingService.php` to determine the max LP awarded per submission and estimate daily farming potential (e.g., "10 LP per submission x unlimited submissions = unbounded daily LP gain")
- Include a 5-step attack scenario narrative: (1) attacker authenticates, (2) submits POST /api/scores with no `type` field or invalid type, (3) daily limit check is skipped, (4) LP is applied, (5) repeat N times per day for unlimited LP farming
- Score the severity: Likelihood HIGH (trivially exploitable by any authenticated user), Impact MEDIUM (LP inflation, not data breach) = MEDIUM overall
- Concern IDs: C-06 (if applicable)
- Remediation: either reject type=null submissions with 422, or apply a separate daily limit for untyped scores, or add a global daily LP cap

**Finding 2 — Daily quiz race condition (SEC-F-013, expected MEDIUM):**
- Trace the SELECT-then-INSERT gap: ScoreController.php line 60 calls `scoreRepository->findTodayByUserAndType()` (a standard SELECT), then at lines 90-102 the INSERT happens inside `wrapInTransaction()`
- The transaction wraps only the INSERT+UPDATE, NOT the SELECT limit check — two concurrent requests can both pass the SELECT simultaneously
- ScoreRepository::findTodayByUserAndType() uses standard Doctrine QueryBuilder with no `SELECT FOR UPDATE` or advisory lock
- No UNIQUE constraint exists on `(user_id, type, played_at::date)` in the Score entity or migrations
- PostgreSQL default isolation is READ COMMITTED — concurrent reads are not blocked
- Include a 4-step attack scenario: (1) attacker sends 2+ parallel POST /api/scores with same valid type, (2) both requests reach line 60, (3) both SELECTs return null (no existing score), (4) both INSERTs commit — user gets 2x LP and 2 score records for one daily slot
- Window size assessment: the SELECT is ~1-5ms, INSERT is ~10-20ms — window is small but exploitable with `curl --parallel` or async fetch
- Severity: Likelihood MEDIUM (requires deliberate parallel tooling), Impact MEDIUM (double LP, not data breach) = MEDIUM
- Concern IDs: C-06
- Remediation: wrap the SELECT in the same transaction with `SELECT FOR UPDATE`, or add a UNIQUE constraint on `(user_id, type, DATE(played_at))`

**Finding 3 — playedAt timezone boundary (SEC-F-014, expected LOW/INFO):**
- ScoreRepository.php uses `new \DateTimeImmutable('today midnight')` which depends on PHP server timezone
- If server runs UTC and user is UTC-12, the "today" boundary resets at a different time than user expects
- This is not a security vulnerability but an edge case that could allow an extra submission around midnight boundaries
- Severity: LOW (informational)

**Clean verdict 1 — JWT identity binding:**
- ScoreController.php line 57: `$this->getUser()` retrieves identity from JWT token, not from request body
- No `user_id` field is accepted in the request body — score is always attributed to the authenticated user
- CLEAN for horizontal privilege escalation (SEC-15 satisfied)

**Clean verdict 2 — Duplicate answer ID inflation:**
- `$data['answers']` is a PHP associative array from `json_decode($request->getContent(), true)`
- PHP's `json_decode` deduplicates JSON object keys — `{"a":"b","a":"c"}` becomes `['a' => 'c']`
- Even if duplicates were possible, `$processed >= $totalQuestions` cap at ScoreController.php lines 73-75 limits iterations
- CLEAN — duplicate answer IDs cannot inflate score
