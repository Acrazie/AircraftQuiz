**Part A: Avatar Upload Findings**

**Finding SEC-F-015 — getimagesize() polyglot bypass risk (expected MEDIUM):**
- Trace ProfileController.php lines 59-67: MIME check via `$file->getMimeType()` (Fileinfo, OS-level) then `getimagesize()` header check
- `getimagesize()` reads image headers only — a valid JPEG/PNG header prepended to malicious content passes the check
- Since R2 serves files via CDN (not executed on server), the risk is stored malicious content delivered to users, NOT server-side RCE
- Severity: Likelihood LOW (attacker must craft polyglot file and be authenticated), Impact MEDIUM (malicious file served to other users via CDN) = MEDIUM
- Concern IDs: C-14
- Remediation: re-encode uploaded images via Intervention Image or Imagine to strip non-image payload bytes; alternatively use `imagecreatefrom*()` + `image*()` round-trip

**Finding SEC-F-016 — Missing image dimension limits (expected LOW):**
- ProfileController.php calls `getimagesize()` which returns `[width, height, type, ...]` but the width/height values are never checked
- A 1KB GIF with `width=65535, height=65535` passes both MIME and getimagesize checks
- When rendered by a client browser via `<img>` tag, this causes client-side memory exhaustion (decompression bomb)
- Severity: LOW (requires deliberate attack, impact is client-side only, users can navigate away)
- Remediation: add `if ($imageInfo[0] > 4096 || $imageInfo[1] > 4096) return 422` after getimagesize check

**Finding SEC-F-017 — Predictable avatar filename strategy (expected LOW):**
- StorageService.php line 46-48: filename is `$user->getId()->toRfc4122() . '.' . $ext`
- UUID is stable per user — every upload overwrites the same R2 key
- An attacker who knows a user's UUID can predict their avatar URL
- Since `putObject` does not set Cache-Control headers, CDN caching behavior is undefined
- This is a precursor to cache poisoning (formally scored in Phase 4 as SEC-20)
- Severity: LOW (informational — cache poisoning risk delegated to Phase 4)
- Concern IDs: feeds SEC-20

**Finding SEC-F-018 — No rate limiting on avatar upload endpoint (expected MEDIUM):**
- POST /api/profile/avatar has no Symfony RateLimiterFactory and no Nginx rate limit
- Each upload triggers a 2MB file transfer + R2 putObject + DB flush
- Repeated uploads = storage cost inflation + bandwidth DoS vector
- Severity: Likelihood MEDIUM (authenticated users only), Impact MEDIUM (operational cost, not data breach) = MEDIUM
- Cross-reference: GAP-04 from Phase 1 trust boundary map (unrate-limited API paths)
- Remediation: add Symfony RateLimiter (e.g., 5 uploads per hour per user)
